# ADR-0005: Drizzle for the schema, PGlite for the suite

Date: 2026-08-19
Status: accepted

## Context
Precedent retrieval needs a vector column and a distance query, and the tables it lands
in are the same tables that will later hold recorded human decisions. That second point
does most of the work here. A recorded decision is the only output this system ships
(ADR-0001), so its storage has to be inspectable and its queries have to be readable by
someone auditing whether a decision could have been written without a reviewer.

The suite has to run in CI without a Postgres service container, and it has to run
against the real schema. A test that passes against a mocked repository proves nothing
about a query the database would reject, and the queries with the most SQL in them are
exactly the ones being introduced.

## Decision
Drizzle for the schema and the queries, with migrations generated by drizzle-kit into
`drizzle/`. PGlite with the pgvector extension in the tests, applying those same
migration files in journal order.

Retrieval accepts a `TriageDatabase` handle rather than reaching for a connection, so the
identical query runs against postgres-js in production and PGlite in the suite. The
connection is built lazily from `DATABASE_URL` on first use, so a missing variable fails
one request rather than the build.

## Alternatives considered
- **Prisma.** Rejected on two counts. `vector` is not a first-class column type, so the
  column arrives through raw SQL and unsafe queries with the type safety hand-written
  around them, which is the wrong place to lose types. And the generated client puts a
  layer between the code and the SQL, where the audit-trail invariants coming in later
  issues want the SQL visible in the file being reviewed.
- **A Postgres service container in CI.** Rejected: it makes the suite an integration
  suite, slow enough that people stop running it locally, and the pgvector image becomes
  a second thing to keep in step with production.
- **Mocking the repository and unit-testing the caller.** Rejected: it tests the mock. A
  wrong distance operator, a missing extension, a vector of the wrong width and an enum
  value outside the recorded outcomes all pass a mock and all fail a database, and three
  of those four are failure modes this schema already has tests for.
- **Raw SQL with no ORM.** Rejected: workable for the query, but the migration story and
  the row types would then be hand-maintained against each other, and the drift would
  land in the table holding adjudications.

## Consequences
Easy: the suite exercises the shipped migration, so an unapplied `CREATE EXTENSION` or a
bad index fails a test rather than a deployment; retrieval is driver-agnostic; the SQL
stays legible in the module that runs it.

Hard: drizzle-kit does not emit `CREATE EXTENSION vector`, so the first migration carries
that line by hand and a future contributor regenerating from scratch has to re-add it.
PGlite is a WASM Postgres and is not byte-identical to the server build, so it is a strong
check rather than a proof; anything version-specific still needs a real instance. We also
carry drizzle-kit as a dev dependency: `npm audit` reports four moderate advisories, all
of them the esbuild development-server issue reaching us through
`drizzle-kit -> @esbuild-kit/esm-loader -> @esbuild-kit/core-utils`, and
`npm audit --omit=dev` reports none, so nothing in that tree is on a shipped path.
